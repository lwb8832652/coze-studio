# MCP 配置状态与本地启用修复设计

## 背景

账号设置中的 MCP 配置面板同时请求自定义服务列表和官方服务目录。当前实现把
`canManage` 初始化为 `false`，只有两个请求都成功后才更新权限。请求返回 `401`
或 `503` 时，页面因此把“请求失败”错误展示成“当前空间为只读权限”。

本地后端同时保持 MCP management/runtime 默认关闭。未显式启用时，MCP 管理
接口按安全策略返回 `503`，不能被前端投影为空列表或只读权限。

## 目标

- 请求生命周期与业务权限完全分离。
- 只有成功响应中的 `can_manage` 才能形成权限结论。
- `401`、`503` 和其它加载异常提供稳定、可理解的页面提示。
- 保留后端默认关闭和失败关闭策略。
- 通过本机忽略配置显式启用 MCP，并在重启后用当前空间管理员账号回归。

## 非目标

- 不修改空间角色和 MCP 服务端鉴权规则。
- 不让关闭状态的 MCP 接口返回伪造的 `200` 或空列表。
- 不在跟踪文件、日志、接口响应或测试夹具中写入真实 MCP 加密密钥。

## 页面状态模型

面板使用以下请求状态：

| 请求状态 | 权限数据 | 页面行为 |
| --- | --- | --- |
| `loading` | 不读取 | 显示加载状态，不显示只读结论，管理操作不可用 |
| `success` | `can_manage=true` | 显示数据并启用管理操作 |
| `success` | `can_manage=false` | 显示数据和“当前空间为只读权限”，管理操作不可用 |
| `error` | 不读取 | 显示错误，不显示只读结论，管理操作不可用 |

两个列表响应都成功后才能进入 `success`。任一请求失败都进入 `error`，并清除上
一次权限结论，避免空间切换或重试后继续展示过期权限。

## 错误投影

- HTTP `401`：提示登录状态已失效，需要重新登录。
- HTTP `503`：提示当前环境未启用或暂时无法提供 MCP 服务。
- 其它错误：使用经过清理的服务端消息；没有安全消息时显示通用加载失败提示。
- 页面不直接展示 Axios 的 `Request failed with status code ...` 文案。

## 本地运行配置

后端继续以 `AGENT_THREAD_MCP_RUNTIME_ENABLED` 作为 MCP management/runtime 的
显式启用事实，并要求 `MCP_AES_AUTH_SECRET` 来加密保存 MCP 凭据。配置只写入本
机忽略的调试环境或本地密钥存储，不进入 Git。

重启前仅检查密钥是否存在和长度是否合法，不输出其内容。缺少密钥时停止启用，
不能生成会在后续重启时丢失的临时密钥。

## 测试与验收

- Vitest 覆盖加载中不显示只读、成功且可管理、成功但只读、`401`、`503`。
- 运行 MCP 配置面板相关测试、前端类型检查和差异检查。
- 重启本地服务后验证两个列表接口返回 `200`。
- 使用当前空间管理员账号打开 MCP 配置，确认不显示只读提示，新建按钮可用，且
  页面无 MCP 列表接口的 `401` 或 `503`。
