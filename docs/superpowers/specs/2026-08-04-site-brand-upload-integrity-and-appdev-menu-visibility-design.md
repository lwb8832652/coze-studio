# 站点品牌上传完整性与 AppDev 菜单可见性修复设计

日期：2026-08-04

## 1. 背景与证据

系统管理的站点 Logo 与 favicon 已保存受控对象 URI，公共站点配置也能生成签名
URL，但页面实际显示破图。对当前运行环境的新鲜诊断结果如下：

- 系统配置预览与工作区标记消费同一组公共品牌 URL；
- 两个 URL 请求均返回 `404`；
- 配置中的 Logo 与 favicon 对象键在当前七牛桶执行元数据查询均返回 `612`，
  即对象不存在；
- 当前上传接口在 `PutObject` 后直接生成 URL，没有确认对象已经可查询；
- 基础配置保存只校验 URI 前缀，没有落实既有站点品牌设计中的对象存在性校验；
- 页面同时保留构建时静态 favicon 和动态 favicon，因此浏览器仍可能显示静态图标，
  掩盖动态配置已经失效的事实。

工作区侧栏同时暴露了尚未进入当前验收范围的“网页应用开发”入口。该能力仍需
保留，当前只临时隐藏入口，不能删除或废弃 AppDev 路由、通知跳转、页面、接口、
Sandbox scope 或运行时能力。

## 2. 目标

- 站点图片只有在对象真实写入并可查询后，上传接口才返回成功。
- 站点配置不能保存不存在的 Logo 或 favicon URI。
- 历史悬空 URI 不再投影成破图，管理员能看出资源不可用并重新上传。
- 浏览器只使用一个生效的动态 favicon；未配置时继续使用内置静态 favicon。
- 工作区 Logo 加载失败时回退到内置标记，不显示浏览器破图占位。
- 暂时隐藏工作区侧栏中的“网页应用开发”，保留所有直接访问和后端能力。

## 3. 非目标

- 不迁移、复制或删除历史对象存储数据。
- 不自动猜测旧 URI 所属的桶，也不自动改写对象存储配置。
- 不改变对象存储控制面的激活、重启和迁移合同。
- 不删除 AppDev 源码、路由、通知目标、后端接口或数据库数据。
- 不把图片二进制、签名 URL、对象存储凭据写入基础配置或日志。

## 4. 方案选择

### 方案 A：只重新上传现有图片

可以短期恢复当前数据，但继续允许保存悬空 URI，切换桶或上传异常后会再次出现。
不作为代码修复。

### 方案 B：只在前端隐藏破图

能改善视觉兜底，但上传仍会错误地返回成功，配置也可能继续保存无效 URI。不能
满足“解决配置上传图片问题”的验收要求。

### 方案 C：上传、保存和消费三层校验（采用）

在现有接口和存储抽象内补齐对象存在性校验，并保留前端失败兜底。改动局部，且
能同时防止新坏数据和历史坏数据继续显示为破图。

## 5. 后端设计

### 5.1 上传完整性

`POST /api/admin/config/site/assets` 保持现有请求和响应合同。图片内容、大小、
尺寸与受控对象键校验不变。对象写入后，处理器必须通过
`upload.SVC.HeadObject` 查询刚返回的 URI：

1. `PutObject` 或 URL 生成失败，返回上传失败；
2. `HeadObject` 查询不到对象，返回上传失败，不向前端返回 URI；
3. 只有写入、查询和 URL 生成都成功时才返回 `200`。

校验不读取对象正文，不新增删除或覆盖操作。日志只能记录资源类型和归一化错误，
不能记录签名 URL、凭据或完整 provider 响应。

### 5.2 保存完整性

`POST /api/admin/config/basic/save` 继续先执行纯字段校验。patch 中的
`site_logo_uri` 或 `favicon_uri` 非空时，再执行对象元数据查询：

- 对象不存在：按无效参数拒绝保存，并指出对应品牌资源需要重新上传；
- 对象存储不可用：按服务端错误返回，不把依赖故障伪装成参数错误；
- 空字符串表示移除自定义资源，不执行对象查询。

没有出现在 patch 中的旧字段不阻断文本配置保存，避免历史悬空资源导致所有基础
配置都不可修改。

### 5.3 公共配置投影

`GET /api/site/config` 为非空品牌 URI 生成 URL 前先查询对象元数据。单个对象不
存在或存储查询失败时，记录脱敏告警并省略对应 URL，不影响站点名称、介绍和另一
个资源的返回。

## 6. 前端设计

### 6.1 系统配置上传与预览

- 上传接口成功后仍先作为表单草稿，不自动保存基础配置；
- 浏览器实际加载预览成功后才接受新的 URI 和预览 URL；
- 预览加载失败时保留原配置草稿，显示“上传资源不可访问，请重试或检查对象存储”
  的明确错误，不展示破图；
- 已保存 URI 非空但公共 URL 为空时显示“资源不可用，请重新上传”，上传按钮允许
  直接替换；
- 保存、移除、revision 冲突和 disabled 行为保持现有合同。

### 6.2 工作区 Logo 与 favicon

- `WorkspaceMark` 对当前 `siteLogoUrl` 记录加载失败状态；失败时回退到现有内置
  SVG，URL 变化后允许重新加载；
- 配置了 favicon 时，文档头部移除构建时的非托管 favicon，只保留带
  `data-coze-site-config` 的动态节点；
- 未配置 favicon 时删除动态节点并保留内置静态 favicon；
- 重复应用同一配置不创建重复节点。

## 7. AppDev 临时隐藏

工作区菜单元数据继续保留 AppDev 项。新增一个命名明确的临时隐藏策略，在最终
可见菜单投影时排除 `SPACE_SUB_MODULE.APP_DEV`。以下能力保持不变：

- `/space/:space_id/app-dev` 与项目详情路由；
- AppDev 页面、服务调用、通知中心直接跳转；
- 后端 AppDev API、Sandbox `appdev` scope 与运行时实现；
- 已有项目数据和测试资产。

`project-context.md` 记录该入口只是阶段性隐藏、功能并未废弃，后续恢复开发时应
移除可见性策略并恢复菜单测试，不重新实现 AppDev。

## 8. 测试与验收

### 后端

- 上传后对象存在才返回成功；查询不到对象时不返回 URI；
- 保存非空 URI 时校验对象存在，空 URI 和未变更字段不查询；
- 公共配置对不存在的单个对象省略 URL，其他品牌字段正常返回；
- 运行相关 Go package 测试。

### 前端

- AppDev 不出现在不同空间角色的工作区侧栏，直接路由和通知映射测试保持通过；
- 上传预览加载成功后才更新草稿，加载失败显示明确错误；
- 工作区 Logo 加载失败回退内置标记；
- 动态 favicon 生效时不存在第二个静态 favicon；
- 运行相关 Vitest、TypeScript 检查和 lint。

### 浏览器回归

使用 `840582614` 系统管理员账号在 `http://localhost:8888` 验证：

1. 上传一张新 Logo 与 favicon，预览立即正常，无品牌资源 `404`；
2. 保存后刷新系统配置，图片仍正常；
3. 进入工作区，左上 Logo 正常且“网页应用开发”菜单不可见；
4. 浏览器 favicon 来自动态配置，head 中不存在重复 favicon；
5. AppDev 直接路由仍可访问，证明功能没有删除；
6. 控制台与品牌资源请求没有新增错误。

当前已经悬空的两个对象不会自动恢复。代码发布后需要由管理员重新上传并保存，
以新 URI 替换历史配置。
