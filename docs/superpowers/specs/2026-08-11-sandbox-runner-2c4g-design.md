# Sandbox Runner 2C4G 混合隔离设计

日期：2026-08-11

## 结论

NewX 不直接部署 RCoder，也不恢复宿主机执行。新增一个 NewX 原生的远程
`sandbox-runner`，继续使用现有 Sandbox Provider 控制面、
`/v1/executions` 合同、容量租约、审计和 fail-closed 边界。

Runner 采用混合生命周期：Agent、AppDev 和 MCP 在严格租户键下短时复用，
Plugin 每次执行创建独立容器。最低兼容基线是 NewX、Web、NSQ 和 Runner 共用
一台 `2C4G` 主机；同一镜像和协议也支持把 Runner 迁移到独立 `2C4G` 节点。

在最低配置下，全机执行权重为 `2`：一个重任务占用两个权重，一个轻任务占用
一个权重，因此只能同时运行一个重任务或两个轻任务。容量不足时任务进入持久化
公平队列，不立即丢弃，也不回退到宿主机。

## 背景与当前事实

仓库已经具备以下能力：

- Sandbox Provider 管理、默认 Provider、健康检查、凭据加密和运行审计；
- `agent`、`appdev`、`mcp_stdio` 和 `plugin` 四类 scope；
- HTTPS remote Provider 的 `/v1/executions`、状态、心跳、取消、恢复、
  AppDev build 和 artifact publish 合同；
- Redis 容量租约、幂等提交、结果不确定时的 lookup/reconcile 和关闭补偿；
- AppDev 使用 `space_id + project_id` 作为运行时复用键；
- 生产和共享环境禁止回退到 host runtime，安全依赖缺失时 fail closed。

当前缺口不是控制面，而是可部署的远程 Runner 执行面，以及它对应的容器隔离、
公平排队、资源水位、生命周期和 `2C4G` 验收实现。现有历史 Nuwax/RCoder 资料只
用于理解来源，不作为新的运行时依赖。

## 目标

- 为 Agent、AppDev、MCP stdio 和 Plugin 提供统一远程执行面；
- 达到空间、用户、项目、会话和单次执行对应的隔离要求；
- 在整机 `2C4G` 共存部署下稳定运行，不以 OOM 作为容量控制手段；
- 支持迁移到独立 Runner 节点而不改变业务 API；
- 容量不足时提供可取消、可超时、可观察的公平队列；
- 保持现有 v1 Provider 合同和第三方 Provider 兼容；
- 对网络、文件、凭据、产物和日志采用默认拒绝及最小授权；
- Runner、Redis、对象存储或容器运行时异常时可恢复且不重复执行。

## 非目标

- 不直接部署、fork 或嵌入 RCoder；
- 不在本阶段恢复“网页应用开发”工作空间菜单；
- 不引入 Kubernetes、Firecracker 或多节点自动扩缩容；
- 不允许 NewX 主进程直接操作 Docker Socket 或执行宿主机命令；
- 不把 Runner 变成用户、任务、权限或最终业务状态的事实源；
- 不为低配环境承诺多个 AppDev 构建或多个 Agent 重任务并发；
- 不在前端或审计中展示原始命令、环境变量、凭据或 Provider 响应。

## 方案比较

### 单个常驻执行容器

所有任务在同一容器内使用不同进程和目录。该方案资源占用最低，但进程、挂载、
环境变量和内核视图共享，跨租户污染和逃逸后的影响面过大，不满足隔离要求。

### 每次执行创建独立容器

每个任务都使用新容器，边界直观且清理简单，但 Agent、AppDev 和 MCP 会频繁冷
启动。在 `2C4G` 下，镜像解压、依赖加载和 AppDev 构建容易造成资源抖动。

### 混合生命周期 Runner

常驻轻量 Runner，根据 scope 和租户键创建或复用执行容器。重工作负载短时复用，
Plugin 保持单次隔离。该方案在隔离、冷启动和低配资源之间最平衡，作为本设计的
正式选择。

## 总体架构

系统分为四个职责清晰的组件。

### NewX 控制面

NewX 后端继续负责：

- 从认证上下文确定用户和空间；
- 校验业务权限和 Sandbox scope；
- 选择健康且可用的 Provider；
- 生成幂等键、策略快照和最小权限授权；
- 保存业务任务状态，投影安全的运行状态和原因码；
- 记录配置审计和运行审计。

NewX 主应用只通过已登记的 HTTPS Provider endpoint 调用 Runner，不直接接触
容器运行时。

### Runner API

`sandbox-runner` 提供已有 `/v1/executions` v1 合同及其状态、心跳、取消、
AppDev build 和产物发布端点。它负责：

- Provider 认证、请求大小、schema 和幂等校验；
- 将已接受请求可靠写入短期队列；
- 按工作空间公平调度；
- 创建、复用、停止和隔离执行容器；
- 投影经过裁剪的执行状态；
- 上传产物并返回受审核 descriptor。

### 调度器与生命周期管理器

调度器维护队列、权重槽位、空间轮转、用户重任务限制和安全水位。生命周期管理器
维护复用键、镜像与策略代次、空闲 TTL、drain 和 quarantine。

### 容器运行层

共机部署使用专属非特权用户下的 rootless 容器运行时。Runner 可以通过受限的
rootless API 管理自己的执行容器，但不能控制宿主机 root Docker daemon。独立节点
部署继续使用同一 Runner 镜像和配置合同。

## 执行数据流

1. 业务入口由 NewX 完成身份、空间、scope 和输入校验。
2. Provider Router 选择已启用、健康且支持目标 scope 的 Provider。
3. NewX 生成稳定幂等键、租户上下文、工作负载类型和策略快照。
4. Runner 在校验通过后先持久化入队，再返回 `accepted`。
5. 调度器按空间轮转和权重规则选择任务，取得本机执行槽位。
6. 生命周期管理器匹配可安全复用的容器，或创建新容器。
7. 容器执行期间通过状态、心跳和取消端点接受控制。
8. 产物通过短期授权上传对象存储，不返回宿主机路径。
9. NewX 将 Provider 状态映射为业务状态、稳定原因码和安全审计。
10. 任务终态后释放执行槽位，并按 scope 立即销毁或进入空闲计时。

## 合同兼容

现有 `coze.sandbox.execute.v1` 保持不变。`accepted` 表示 Provider 已可靠接收请求，
任务此时可以仍在队列中。旧 Provider 和旧客户端不需要理解新的内部队列状态。

Runner 新增可选 capability `queue_status_v1`。支持该 capability 时，NewX 可以通过
独立队列状态端点读取以下安全字段：

- 是否正在等待资源；
- 近似队列位置；
- 预计等待秒数；
- 排队截止时间；
- 可取消状态；
- 稳定原因码。

该端点不返回其他租户信息、原始请求、资源配置或调度器内部键。第三方 Provider
不支持该 capability 时，NewX 只显示“等待资源”，不显示位置和预计时间。

## 租户与容器隔离

### 复用键

| Scope | 复用键 | 生命周期 |
| --- | --- | --- |
| Agent | `space_id + user_id` | 空闲 5 分钟后销毁 |
| AppDev | `space_id + project_id` | 空闲 10 分钟后销毁 |
| MCP stdio | `space_id + session_id` | 空闲 3 分钟后销毁 |
| Plugin | `space_id + execution_id` | 执行完成立即销毁 |

复用键必须来自服务端认证事实或受信业务记录，不能接受客户端自行声明的 owner。
任何键字段缺失或不一致时 fail closed。

### 容器约束

执行容器必须：

- 使用非 root 用户和独立用户命名空间；
- 使用只读根文件系统；
- 设置 `no-new-privileges`，移除非必要 Linux capabilities；
- 使用默认拒绝的 seccomp/AppArmor 等等价策略；
- 限制 CPU、内存、PID、文件描述符、输出字节和最大运行时长；
- 不挂载宿主机 Docker Socket、设备、控制目录或任意宿主机路径；
- 为 `/tmp` 使用任务独立 tmpfs；
- 只挂载与复用键匹配的工作卷；
- 禁止跨租户容器、进程、网络命名空间和工作卷访问。

每次复用前必须终止残留进程、清空任务级临时目录和凭据，并执行轻量健康检查。
清理不完整的容器不能再次分配。

## 文件、依赖和产物

基础镜像不可变并使用 digest 固定版本。工作卷仅保存该复用键允许保留的工作区文件，
不保存任务级凭据、临时输出和控制面元数据。

依赖下载默认不直接访问公网，而是通过受控代理缓存。缓存按生态和完整性摘要组织，
不可混入用户工作卷，也不能把一个租户上传的未审核文件作为其他租户的依赖。

产物上传使用短期、单次、限定对象前缀和大小的授权。Runner 和容器不持有对象存储
长期 AK/SK。NewX 只接收经过审核的 artifact descriptor，不接收宿主机绝对路径。

## 凭据隔离

任务凭据采用单 scope、单执行、短有效期授权。优先以内存或 tmpfs 文件注入；只有
第三方工具明确要求时才投影为进程环境变量。环境变量投影必须限定到目标进程，任务
结束后销毁，且不能进入镜像、工作卷、快照、错误正文或日志。

Provider credential keyring、active key id 和 Runner 身份仍由 Secret Manager 或
部署环境管理。读取 API 不返回明文凭据。轮换时新任务使用新代次，旧容器进入 drain，
不得在不同 credential generation 间复用。

## 网络策略

执行容器默认无外网访问。每个 Provider policy 可以按 scope 配置域名和端口白名单，
但以下目标始终拒绝：

- 云元数据地址；
- 回环和未授权私网地址；
- 宿主机网关和容器控制接口；
- NewX 管理 API 和 Secret 管理端点；
- 未登记的代理或 DNS 旁路。

网络策略必须在容器外层执行，不能仅依赖用户进程自律。DNS 解析结果发生变化时重新
校验目标地址，避免域名重绑定绕过。

## 2C4G 资源模型

最低基线是 NewX、Web、NSQ 和 Runner 共用一台 `2C4G` 主机。MySQL、Redis、
Elasticsearch 和对象存储按当前 dev 架构使用远程服务。

### 权重

| 工作负载 | 分类 | 权重 | 默认单任务上限 |
| --- | --- | --- | --- |
| Agent | 重 | 2 | 约 `1.25 CPU / 1.5 GB` |
| AppDev | 重 | 2 | 约 `1.25 CPU / 1.5 GB` |
| MCP stdio | 轻 | 1 | 约 `0.4 CPU / 384 MB` |
| Plugin | 轻 | 1 | 约 `0.4 CPU / 384 MB` |

最低配置总权重为 `2`。因此只允许运行一个重任务或两个轻任务，重任务与轻任务不
混跑。Runner 常驻内存预算约为 `128 MB`。

系统必须至少为宿主机、NewX、Web 和 NSQ 保留 `1.5 GB` 内存。安全水位不足时暂停
出队；已经运行的任务按 cgroup 限制继续或失败，不能通过继续启动任务等待 OOM。

独立 Runner 节点使用相同权重模型，只调整总权重和单任务额度。资源参数必须经过
上下界校验，不能由单个业务请求覆盖。

## 队列与公平调度

Runner 使用开启持久化的 Redis 保存短期队列和调度状态。执行信封必须加密并设置
TTL；Redis 不保存长期业务事实。Redis 状态丢失时，由 NewX 使用原幂等键执行
lookup/reconcile，禁止生成新的逻辑执行。

### 两层容量控制

现有 Provider Router 在调用 Runner 前取得容量租约，因此不能继续把该租约直接等同
于本机 CPU/内存运行槽位，否则容量已满的请求无法进入 Runner 队列。Native Runner
采用两层容量控制：

- NewX 准入层限制单个 Provider 的“已接受但未终结”执行总数，防止队列无限增长；
- Runner 执行层使用权重和安全水位限制实际运行容器数量。

Native Runner 通过 `queue_status_v1` capability 声明支持排队，并使用独立的
`max_outstanding` 准入上限。现有 `MaxConcurrency` 对不支持排队的第三方 Provider
保持原语义，不做全局重解释。Native Runner 的队列还必须配置全局、单空间和单用户
深度上限；超过上限时返回明确的 `CAPACITY_UNAVAILABLE`，而不是无限接受。

排队期间 NewX 继续维护准入租约和执行 checkpoint。应用或网络重启后必须通过原
幂等键和 Provider execution id 恢复，不能因租约重建而提交第二次逻辑执行。

公平规则如下：

- 工作空间之间轮转；
- 空间内部按提交时间执行；
- 同一用户最多一个运行中的重任务；
- 同一 AppDev 项目的构建和工作卷修改必须串行；
- 两个轻任务可以填满两个轻任务槽；
- 重任务运行时轻任务等待，不进行任务抢占；
- 队列位置为近似值，预计等待时间使用同类任务近期耗时的移动估计；
- 排队中任务可以由授权用户取消。

默认排队超时：

- Plugin 和 MCP：5 分钟；
- Agent：10 分钟；
- AppDev：20 分钟。

达到截止时间后任务进入明确终态并返回 `QUEUE_TIMEOUT`，不能静默延期。

## 生命周期与回收

容器只有在复用键、镜像 digest、运行策略版本和凭据代次全部相同时才可复用。
任一项变化都使旧容器进入 drain。

排队中取消直接删除队列项并释放相关租约。运行中取消先发送正常终止信号，超过配置
的宽限期后强制结束。心跳只能延长已授权会话的空闲时间，不能突破任务最大运行时长。

Runner 重启后恢复未完成队列和运行记录。对于提交结果不确定的请求，只能用同一
幂等键查询或重放。容器清理失败时进入 quarantine 并异步重试；在清理成功或人工
处置前不能复用。

## 动态配置

日常参数在系统管理“沙箱管理”中维护，不放入 `app.env`：

- 总执行权重和各 workload 权重；
- CPU、内存、PID 和最大执行时长；
- 各 scope 排队超时和空闲 TTL；
- 系统内存安全水位；
- 取消宽限期；
- 熔断、恢复和健康检查阈值；
- 网络和依赖代理策略。

配置持久化到数据库并带单调版本号。Runner 只接受由 NewX 签发且仍在有效期内的完整
配置快照；更新必须整体校验，不能部分生效。配置变更只影响新任务，已运行任务继续
使用启动时快照。

`app.env` 只保留控制面和运行路由总开关、credential keyring、Redis 连接、Runner
身份及紧急 fail-closed 开关。

## 状态与稳定错误

前端只展示用户可行动的稳定原因码：

| 原因码 | 含义 | 默认动作 |
| --- | --- | --- |
| `QUEUE_TIMEOUT` | 排队超过截止时间 | 可重新提交 |
| `CAPACITY_UNAVAILABLE` | 当前资源低于安全水位 | 保持排队或稍后重试 |
| `POLICY_DENIED` | 文件、网络或命令违反策略 | 修改配置或输入 |
| `RUNTIME_START_FAILED` | 执行容器未能启动 | Runner 可安全重试启动阶段 |
| `EXECUTION_TIMEOUT` | 超过最大运行时长 | 终止当前任务 |
| `ARTIFACT_PUBLISH_FAILED` | 代码完成但产物发布失败 | 只重试产物发布 |
| `RUNTIME_QUARANTINED` | 容器清理失败 | 禁止复用并后台清理 |
| `PROVIDER_UNAVAILABLE` | Runner 或必要依赖不可用 | fail closed |

Runner、容器运行时和用户代码的原始错误只进入受控内部诊断，必须经过脱敏并限制保留
时间。公共错误不能包含命令、环境变量、凭据、内部路径、endpoint 或 Provider body。

## 故障恢复

- Redis 不可用时拒绝新任务，但尽量保留已有任务的状态查询和取消；
- 对象存储失败只重试产物发布，不重新执行用户代码；
- Provider 连续异常后暂停出队并熔断，健康恢复后逐步放量；
- 只有网络中断、提交结果不确定和明确幂等的准备阶段允许自动重试；
- 用户代码明确失败、超时或取消后不自动重跑；
- capacity lease、执行状态和容器回收必须单调，迟到响应不能回退终态；
- 任何恢复路径都不能切换到宿主机、其他租户或未登记 Provider。

## 可观测性与管理页面

在现有 Sandbox 指标基础上增加低基数指标：

- 各 scope 队列深度和等待时长；
- 权重槽位使用量；
- 容器冷启动、复用、drain、销毁和 quarantine 次数；
- 安全水位暂停次数；
- 队列超时和取消次数；
- Runner 恢复与 reconciliation 结果。

标签只能包含 scope、workload、结果、稳定原因码和状态，不能包含用户、空间、项目、
执行 ID、endpoint 或凭据。

系统管理页展示 Provider 健康、当前配置版本、队列深度、运行槽位、内存水位、
draining/quarantine 数量和最近稳定原因码。运行审计继续使用裁剪后的关联号。

## 验证策略

### 单元和合同测试

- v1 execute/status/keep-alive/cancel/build/artifact 合同保持严格兼容；
- `queue_status_v1` capability 和安全投影；
- scope、复用键、策略版本和 credential generation 匹配；
- 权重、空间轮转、用户重任务限制、超时和取消；
- 迟到状态、重复提交、重复取消和重复回收保持幂等；
- 动态配置上下界、版本和整体生效。

### 集成和故障测试

- rootless 容器创建、限制、停止、强制结束和销毁；
- Runner、Redis、对象存储和容器运行时中断；
- 重启恢复、lookup/reconcile 和 quarantine；
- Agent、AppDev、MCP 和 Plugin 的真实最小任务；
- 产物授权过期、大小越界和重复发布。

### 安全测试

- 跨空间、跨用户、跨项目和跨会话工作卷访问失败；
- 无法读取其他容器进程、环境变量、凭据和产物；
- root、提权、Docker Socket、宿主机网关和设备访问失败；
- 云元数据、私网、DNS 重绑定和未授权代理访问失败；
- 日志、数据库、工作卷、快照和产物不包含明文密钥。

### 2C4G 实机验收

- NewX、Web 和 NSQ 正常运行时，一个重任务成功完成；
- 第二个重任务进入队列，不触发宿主机 OOM；
- 两个轻任务并行，第三个进入队列；
- 重任务运行时轻任务等待且不抢占；
- CPU、内存、PID 或超时越界只终止对应任务；
- 四类 scope 各完成一次真实执行；
- 排队位置、预计等待、取消、超时和稳定错误提示可见；
- 容器回收后内存和工作卷占用回落到基线；
- 页面和浏览器控制台无未处理错误。

## 上线顺序

1. 部署 Runner，保持 `SANDBOX_RUNTIME_ROUTING_ENABLED=false`。
2. 注册 remote Provider，验证健康、凭据、策略同步和配置版本。
3. 开放 Plugin 和 MCP 轻任务，验证两个轻槽及排队。
4. 开放 Agent 重任务，验证独占权重和用户公平限制。
5. 开放 AppDev build/preview，验证项目串行、复用和产物发布。
6. 每一阶段都执行故障和取消路径；异常时关闭对应 scope。
7. 所有阶段稳定后，再单独评估恢复“网页应用开发”菜单入口。

## 完成标准

只有同时满足以下条件，Runner 才能视为完成：

- 现有四类 scope 均通过远程 Provider 真实执行；
- v1 合同兼容测试通过，第三方 Provider 未受影响；
- `2C4G` 共机验收通过且无宿主机 OOM；
- 租户、文件、网络和凭据隔离测试通过；
- 排队、公平、取消、超时、恢复和 quarantine 路径通过；
- 系统管理配置、状态、指标和审计均只展示安全字段；
- 运行依赖不可用时全链路 fail closed；
- 运维手册覆盖共机、独立节点、密钥轮换、熔断和恢复。
