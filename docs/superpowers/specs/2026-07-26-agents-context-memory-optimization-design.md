# AGENTS 与长期项目上下文优化设计

## 背景

当前 `AGENTS.md` 仍以早期 Nuwax 对齐阶段为主线，包含一期菜单、历史分支、
参照环境和大量阶段性硬规则。项目已经进入 Coze 原生能力的内部优化阶段，
这些内容继续默认加载会挤占上下文，也会误导后续任务把 Nuwax 当作当前产品
事实。

项目已安装并初始化两类本地知识工具：

- `codebase-memory`：持久化代码结构、符号、调用链和变更影响；
- `graphify`：建立精选文档、架构决策和跨文档概念关系的长期图谱。

本次优化将仓库入口、长期事实、操作手册和历史资料分层，并建立需求分支合入
本地 `dev`、再同步远程 `origin/dev` 的双重审计门禁。

## 目标

1. 将 `AGENTS.md` 收敛为短入口，只保留高频工作规则和不可破坏的边界。
2. 将当前项目架构、产品边界和有效技术决策放入可维护的长期上下文文档。
3. 将 Nuwax 从默认开发基线降级为按需读取的历史参考。
4. 明确 `codebase-memory` 与 Graphify 在分析、开发、验收和上下文更新中的职责。
5. 每个需求完成后先审计需求分支，经用户确认后合入本地 `dev`；合入后执行
   更严格的第二次审计，经用户再次确认后才允许推送 `origin/dev`。
6. 防止本地 `dev` 落后、远程并发更新、多个 worktree 或旧功能分支造成版本
   冲突和未审计代码混入。

## 非目标

- 不删除历史 Nuwax、DeerFlow 或阶段性 plans/specs；
- 不把 Graphify 全仓图谱或 codebase-memory 数据库提交到 Git；
- 不在本次修改业务代码、运行时合同、数据库结构或产品页面；
- 不引入自动合并、自动推送、force push 或绕过用户确认的脚本；
- 不要求每个小修复都新增架构文档，只有长期事实变化时才更新上下文。

## 文档分层

### `AGENTS.md`

根文件继续作为 Codex 的默认入口，目标是让新任务在较小上下文内获得正确的
工作方式。保留以下内容：

- 当前项目定位和核心技术栈；
- 事实来源和上下文读取顺序；
- 代码分析工具协议；
- 任务分析、实施和验证基线；
- 前端、后端、Agent Runtime、IDL、安全和危险操作红线；
- 双重审计和用户确认门禁；
- 本地调试及专题文档索引。

移出或降级以下内容：

- “当前一期”“当前集成目标”等已完成阶段说明；
- Nuwax 默认参照路径、账号和页面对齐要求；
- `codex/coze-nuwax-management-mainline` 等过期日常分支约定；
- 只服务单一历史需求的菜单位置、迁移顺序和验收细节；
- 已在 runbook 或专题 spec 中完整描述的长篇运行参数。

### `docs/superpowers/context/project-context.md`

新增长期事实入口，记录：

- 当前产品定位和内部优化方向；
- 前端、后端、执行内核、控制面和基础设施的稳定边界；
- 主要目录和事实来源；
- 当前有效的安全、租户、权限和数据合同；
- 仍在使用的专题设计与 runbook 索引；
- 更新条件、负责人行为和过期信息处理方式。

该文件只记录跨任务长期有效的事实，不记录一次性任务状态或大段实施日志。

### `docs/superpowers/runbooks/dev-integration-audit.md`

新增可执行的 Git 集成手册，记录两次审计的命令、证据、停止条件、用户确认点
和远程同步规则。`AGENTS.md` 只保留摘要并链接到该手册。

### 历史资料

既有 Nuwax plans/specs 保持原路径，作为历史决策和问题追溯资料。只有任务明
确要求排查历史迁移、回归或行为来源时才读取；不得把历史文档中的产品形态、
分支名或验收口径自动当作当前事实。

## 两套知识工具的职责

### codebase-memory

用于代码结构和影响分析：

1. 开工时检查项目索引和新鲜度；
2. 用 `get_architecture`、`search_graph`、`trace_path` 理解现有边界；
3. 修改前查询调用方、被调用方和跨层依赖；
4. 修改后用 `detect_changes` 检查影响面和风险；
5. 架构决策发生变化时记录 ADR，并同步到受版本控制的长期文档。

图谱结果是导航证据，不替代源码、测试、IDL、迁移和运行时验证。索引过期、
路径缺失或结果与源码冲突时，以当前源码和运行现象为准并刷新索引。

### Graphify

用于精选上下文和跨文档关系：

1. 只索引长期上下文、有效架构说明、关键 runbook 和活跃设计；
2. 方案阶段查询跨模块概念、历史决策和文档之间的关系；
3. 上下文文档变化后运行增量更新；
4. 查询结果必须带回具体来源文件核实；
5. 不默认对 15,000 余文件的整个 monorepo 建立 Graphify 图谱。

`graphify-out/` 是本机缓存并加入忽略规则，不提交大型 JSON、HTML 或临时检测
文件。团队可审计的事实必须写入 Markdown、代码、测试或提交历史。

## 需求开发上下文周期

### 开工

1. 读取 `AGENTS.md`、`project-context.md` 和与任务直接相关的 runbook/spec；
2. 检查当前分支、工作区、worktree、远程跟踪关系和用户已有改动；
3. 使用 codebase-memory 获取架构、调用链和预期影响；
4. 只有涉及跨文档或历史决策时才查询 Graphify；
5. 明确任务范围、验证方式和是否会改变长期事实。

### 实施

1. 在独立 `codex/` 需求分支开发，不直接在 `dev` 上写功能；
2. 遵循现有目录、合同、生成 client 和测试风格；
3. 图谱与源码不一致时停止推断，回到源码和运行态核实；
4. 只在架构、合同、安全或运维事实变化时更新长期上下文；
5. 保留任务验证证据和已知风险，不把临时状态写入 `AGENTS.md`。

### 完成

1. 运行与风险相匹配的测试、构建、类型检查和页面验收；
2. 使用 codebase-memory 检查最终变更影响；
3. 更新受影响的上下文、ADR、runbook 或活跃计划；
4. 上下文语料变化时增量更新 Graphify；
5. 进入第一次集成审计，禁止自动合入或推送。

## 第一次审计：合入本地 dev 前

第一次审计在需求分支执行，目标是证明需求本身正确且基于最新 `dev`。

必查项：

1. `git fetch origin dev` 后记录 `origin/dev`、本地 `dev`、需求分支和审计提交
   的 SHA；
2. 检查 `git status`、`git worktree list`、分支领先/落后关系和未提交文件；
3. 确认本地 `dev` 能以 fast-forward 方式对齐 `origin/dev`，若两者分叉则停止；
4. 将已 fetch 的 `origin/dev` 合入需求分支，在需求分支解决冲突并重新验证，
   第一次审计期间不得改动本地 `dev`；
5. 审核完整 diff、提交列表、无关文件、生成代码、迁移、锁文件和敏感信息；
6. 运行相关测试、构建、静态检查、页面验收和 codebase-memory 影响分析；
7. 输出审计报告：基准 SHA、需求 SHA、文件范围、验证结果、风险和未决事项。

只有审计通过且用户明确确认后，才能先 fast-forward 本地 `dev` 到审计使用的
`origin/dev` 基准，再合入已审计的需求提交。第一次确认不包含远程推送授权。

## 第二次审计：合入本地 dev 后

第二次审计必须从合并后的本地 `dev` 重新执行，范围和证据要求高于第一次：

1. 重新 `git fetch origin dev`，确认远程基准未在合并后变化；
2. 核对 `origin/dev...dev`，确保只包含用户批准的需求提交和预期合并提交；
3. 从本地 `dev` 重新运行相关测试，不复用需求分支结果；
4. 对共享合同或高风险模块补充跨包测试、构建、类型检查和真实页面验收；
5. 扫描冲突标记、重复实现、迁移顺序、生成文件漂移、敏感信息和无关改动；
6. 再次运行 codebase-memory 影响分析，核实最终调用链和反向依赖；
7. 上下文变化时检查 Graphify 关系和当前决策是否矛盾；
8. 记录合并前后 SHA、最终 diff、完整验证证据和剩余风险。

第二次审计通过后仍必须获得用户第二次明确确认，才允许执行
`git push origin dev`。禁止 force push。若远程 `dev` 在审计期间前进、推送被
拒绝或发现额外提交，停止同步，重新对齐需求分支并从第一次审计开始。

推送成功后核对远程 SHA；远程 SHA 与本地 `dev` 不一致时不得宣称同步完成。

## 失败与降级

- codebase-memory 或 Graphify 不可用时，使用 `rg`、源码、Git、测试和运行态
  证据继续工作，并在结论中记录缺失的图谱验证；
- 图谱索引过期时先刷新，再做影响或历史关系结论；
- worktree 被占用、工作区不干净、分支分叉或相关用户改动无法隔离时停止合并；
- 测试、构建、页面验收或安全扫描失败时不得进入用户确认门禁；
- 用户确认只对报告中列出的 SHA 和范围有效，提交变化后必须重新审计。

## 实施范围

本设计批准后的实施只修改以下文档和忽略规则：

- `AGENTS.md`；
- `docs/superpowers/context/project-context.md`；
- `docs/superpowers/runbooks/dev-integration-audit.md`；
- `docs/superpowers/runbooks/local-debug-and-test.md`；
- `.gitignore` 中的 Graphify 本地缓存规则；
- 本设计对应的实施计划。

## 验证与完成标准

1. `AGENTS.md` 不再把 Nuwax、一期迁移或旧日常分支当作默认主线；
2. 所有从 `AGENTS.md` 指向的本地文档路径存在；
3. 项目上下文明确描述当前内部优化阶段和稳定架构边界；
4. 两套知识工具有明确的使用时机、新鲜度检查和降级路径；
5. 双重审计包含两次独立用户确认，第二次验证严格于第一次；
6. `graphify-out/` 不进入 Git 变更；
7. 通过旧规则残留扫描、链接检查、`git diff --check`、精选语料检测和
   codebase-memory 可用性检查；
8. 不修改或提交用户已有的无关文件。
